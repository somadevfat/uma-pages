# 個人ブログ構築 要件定義書（確定版たたき台）

作成日: 2025-12-27

## 1. プロジェクト概要（目的・目標）

### 1.1 背景
- 学習記録を継続的に残したい（アウトプット習慣化）
- 転職活動時に「キャリア・実力・継続性」を伝えたい
- ブログ感覚の日記投稿も含め、GitHubのコミットを増やしつつ実績化したい

### 1.2 目的（Why）
- 採用面接者が短時間で「何ができるか・どこまで自走できるか」を把握できる状態を作る
- 学習ログを蓄積し、再利用できるナレッジベースにする
- 継続運用しやすい仕組みで更新を止めない

### 1.3 目標（KGI/KPI案）
- KGI: ブログ（Portfolio/学習記録）を見れば実力と継続性が分かる状態
- KPI（暫定）
  - 週1本以上の投稿（短文ログ含む）
  - Portfolioを制作物完成ごとに更新
  - SEOを狙う技術記事を月1〜2本

---

## 2. ターゲットユーザーと提供価値

### 2.1 ターゲット読者
- エンジニア全般
- 採用面接者（面接官/採用担当）

### 2.2 提供価値
- **ポートフォリオ**：制作物・技術選定理由・工夫点・改善計画を一覧化
- **学習記録**：学習内容＋詰まりポイント＋解決策を再現可能な形で蓄積
- **技術記事**：検索意図に合う具体性（手順、比較、検証結果）

---

## 3. 機能要件

> 方針確定: 投稿は **A) MarkdownをGitで管理**、公開範囲は **全公開**。

### 3.1 記事投稿（Git運用）
- 記事作成・編集: Markdown（必須）
- 記事属性（frontmatter想定・必須/推奨）
  - `title`（必須）
  - `slug`（必須）
  - `date`（必須）
  - `updated`（任意）
  - `description`（必須推奨：SEO/OGP用概要）
  - `category`（必須：1つを基本）
  - `tags`（任意）
  - `heroImage`（任意）
  - `draft`（必須：下書き制御用 boolean）
- 表示要件
  - 目次自動生成（推奨）
  - コードブロックのシンタックスハイライト（必須）
  - 画像表示（必須）

### 3.2 下書き（確定）
- `draft: true` の記事は本番ビルドで **非公開（一覧・詳細とも除外）**
- 下書き確認はローカル環境（またはプレビュー環境）で実施
  - 追加要件（任意/将来）: URLを知っている人だけ見られるプレビュー機能は **現時点では不要**

### 3.3 カテゴリ・タグ
- カテゴリ一覧ページ（必須）
- カテゴリ別記事一覧（必須）
- タグ一覧/タグ別記事一覧（任意：記事数増加後でも可）

### 3.4 検索
- サイト内検索（必須）
  - 対象: タイトル/概要（必須）、本文（可能なら）
  - 実装方式: 小規模は静的インデックス、増えたらサーバ検索に拡張可能な設計

### 3.5 固定ページ
- About（必須）
- Portfolio（必須）
- Contact（必須）

### 3.6 SNS/外部連携
- RSS/Atomフィード（必須推奨）
- 記事共有ボタン（X/LinkedIn等）（任意）

### 3.7 SEO
- メタタグ（title/description）自動設定＋記事単位で上書き（必須）
- OGP/Twitterカード（必須）
- sitemap.xml / robots.txt（必須）
- canonical（必須）
- 構造化データ（任意だが推奨）

### 3.8 お問い合わせフォーム（必須）
- 公開サイトにContactページを用意
- フォーム項目（暫定）
  - name（任意）
  - email（必須）
  - subject（任意）
  - message（必須）
- スパム対策（必須）
  - honeypot
  - rate limit（IP/UA単位など）
  - 入力バリデーション

### 3.9 管理画面（必須）
- 目的: 問い合わせを管理画面で閲覧・対応できるようにする
- 対象機能（必須）
  - 問い合わせ一覧（新着/既読フィルタ）
  - 問い合わせ詳細
  - 既読/未読の更新
- 認証（必須）
  - MSAL（Microsoft Entra ID）でログイン
  - 管理画面APIはJWT（Bearer）で保護
  - 1人運用のため `oid`（object id）allowlistで管理者認可

## 4. 非機能要件

### 4.1 パフォーマンス
- 目標: 読み込みが速く、可読性を損なわない（Core Web Vitalsを意識）
- 基本方針: 記事ページは静的生成（SSG/ISR）寄り

### 4.2 セキュリティ
- 管理画面
  - 認証必須、HTTPS必須
  - 権限: 管理者のみ（当面は単一ユーザー想定）
- お問い合わせ
  - rate limit / バリデーション / ログ
- 依存関係の脆弱性対応
  - 定期アップデート（運用で担保）

### 4.3 保守性・拡張性
- Markdown（コンテンツ）とUI（表示）を疎結合に
- frontmatterスキーマを固定し、将来の移行が可能な構造に

### 4.4 レスポンシブ
- モバイル/PC両対応（必須）
- 本文の行幅、行間、コードブロックの横スクロールを最適化

## 5. デザイン方針（トーン＆マナー、UI/UX）

### 5.1 トーン＆マナー
- **モダン**、シンプル、見やすい
- 「AIっぽくない」= テンプレ臭・過剰装飾・煽りを避ける
- タイポグラフィと余白を重視

### 5.2 UI方針
- 迷わない導線（例: Home / Categories / Portfolio / About / Contact）
- 採用面接者向けにPortfolio導線を強化

### 5.3 UIライブラリ
- **MUIは使用しない（確定）**
  - 理由: コンポーネント既視感が出やすく、狙うトーン（シンプルでAIっぽくない）とズレる可能性
- 代替案
  - Tailwind CSS（候補）
  - CSS Modules + 最小コンポーネント自作（候補）

### 5.4 ダークモード（確定）
- ダーク/ライト切替トグル（必須）
- `prefers-color-scheme` に追従（初期値）
- ユーザー選択を永続化（localStorage/Cookie等）

## 6. 推奨技術スタック（Next.js, Hono）

### 6.1 フロント
- Next.js
- Markdown処理: remark/rehype または MDX（必要性は実装で最終判断）
- コードハイライト: Shiki等（推奨）

### 6.2 バックエンド/API
- Hono
  - お問い合わせ送信API
  - 管理画面用API（問い合わせ一覧/更新）

### 6.3 DB（問い合わせ保存）
> 管理画面要件があるため、問い合わせはDBに保存する。

- 推奨: PostgreSQL（マネージド: Supabase/Neon 等）
- DB設計（概念→論理）は別紙に分離
  - `docs/requirements/database/01-conceptual.md`
  - `docs/requirements/database/02-logical.md`

### 6.4 デプロイ（暫定）
- Next.js: Vercel等
- Hono: Workers等
- 構成は「管理画面 + DB」前提で、運用しやすい組合せを採用

---

## 7. 運用・保守計画

### 7.1 更新運用
- 記事: Markdownを追加/更新 → Git push → 自動デプロイ
- 下書き: `draft: true` でmainに置いても本番には出さない（ただし運用ルールは明確化する）

### 7.2 バックアップ
- 記事: Gitがバックアップ
- 問い合わせ: DBの定期バックアップ（週次 or 月次）

### 7.3 保守
- 依存関係更新（目安: 月1）
- スパム状況を見て対策強化（CAPTCHA導入は最終手段）
